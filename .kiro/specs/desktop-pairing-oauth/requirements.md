# Requirements Document

## Introduction

This feature replaces the external OAuth provider (Auth0) with a self-issued OAuth 2.1 authorization server built into the xoxo MCP server at aix.reflect.systems. Authentication is backed by short-lived desktop pairing codes rather than user accounts. The flow allows ChatGPT's MCP app to discover the server's OAuth metadata, present a pairing code entry page, and exchange an authorization code for a self-issued JWT access token that maps to the paired desktop WebSocket session. Write tools require desktop-side confirmation before executing; read tools work immediately after pairing.

## Glossary

- **MCP_Server**: The xoxo Node.js HTTP server at aix.reflect.systems implementing both the MCP protocol and the OAuth 2.1 authorization server
- **Desktop_App**: The xoxo Electron desktop application that initiates pairing and maintains a WebSocket connection to the MCP_Server
- **ChatGPT_App**: The ChatGPT MCP client application that discovers OAuth metadata, authenticates via the pairing flow, and invokes MCP tools
- **Pairing_Code**: A short-lived, human-readable code in the format XOXO-XXXX-XXXX (4 alphanumeric characters after the prefix) generated by the MCP_Server and displayed in the Desktop_App for the user to enter in the authorization page
- **Authorization_Server**: The OAuth 2.1 authorization server functionality built into the MCP_Server (no external provider)
- **Access_Token**: A self-issued JWT signed with a server-side secret that identifies a paired desktop session
- **Authorization_Code**: A short-lived opaque code issued after successful pairing code confirmation, exchangeable for an Access_Token at the token endpoint
- **Desktop_Session**: The WebSocket connection from the Desktop_App to the MCP_Server, identified by a session ID and linked to a Pairing_Code during the pairing flow
- **Write_Tool**: An MCP tool that modifies circuit state (optimize_component, set_circuit_layout, add_component, remove_component, add_wire, remove_wire, move_component, begin_edit_group, end_edit_group)
- **Read_Tool**: An MCP tool that retrieves data without modifying state (get_circuit_layout, get_frequency_response, get_impedance_response, get_user_loaded_frds)
- **OAuth_Metadata**: The JSON document at /.well-known/oauth-authorization-server describing the Authorization_Server's endpoints and capabilities
- **Protected_Resource_Metadata**: The JSON document at /.well-known/oauth-protected-resource describing the MCP_Server as an OAuth resource server and pointing to its authorization server (RFC 9728)
- **Resource_Parameter**: The `resource` parameter (RFC 8707) included in authorization and token requests that identifies the MCP_Server as the intended audience for the token

## Requirements

### Requirement 1: OAuth 2.1 Metadata Discovery

**User Story:** As the ChatGPT_App, I want to discover the MCP_Server's OAuth endpoints via a standard metadata document, so that I can initiate the authorization flow without hardcoded endpoint URLs.

#### Acceptance Criteria

1. THE MCP_Server SHALL serve a JSON document at the path `/.well-known/oauth-authorization-server` that conforms to RFC 8414 (OAuth 2.0 Authorization Server Metadata)
2. THE OAuth_Metadata document SHALL include the `issuer` field set to `https://aix.reflect.systems`
3. THE OAuth_Metadata document SHALL include the `authorization_endpoint` field set to `https://aix.reflect.systems/oauth/authorize`
4. THE OAuth_Metadata document SHALL include the `token_endpoint` field set to `https://aix.reflect.systems/oauth/token`
5. THE OAuth_Metadata document SHALL include `code_challenge_methods_supported` containing `S256` to indicate PKCE support
6. THE OAuth_Metadata document SHALL include `response_types_supported` containing `code`
7. THE OAuth_Metadata document SHALL include `grant_types_supported` containing `authorization_code`
8. THE MCP_Server SHALL return the OAuth_Metadata document with Content-Type `application/json` and a 200 status code
9. THE OAuth_Metadata endpoint SHALL be accessible without authentication

### Requirement 1b: Protected Resource Metadata (RFC 9728)

**User Story:** As the ChatGPT_App, I want to discover which authorization server protects the MCP endpoint, so that I can initiate the correct OAuth flow.

#### Acceptance Criteria

1. THE MCP_Server SHALL serve a JSON document at the path `/.well-known/oauth-protected-resource` that conforms to RFC 9728 (OAuth 2.0 Protected Resource Metadata)
2. THE Protected_Resource_Metadata document SHALL include the `resource` field set to `https://aix.reflect.systems/mcp`
3. THE Protected_Resource_Metadata document SHALL include the `authorization_servers` field containing `["https://aix.reflect.systems"]`
4. THE Protected_Resource_Metadata endpoint SHALL be accessible without authentication
5. WHEN the MCP_Server returns a 401 Unauthorized response, THE response SHALL include a `WWW-Authenticate` header with `Bearer realm="https://aix.reflect.systems"` and `resource_metadata="https://aix.reflect.systems/.well-known/oauth-protected-resource"`
6. THE MCP_Server SHALL accept a `resource` parameter (RFC 8707) in authorization and token requests and bind the issued token's audience to that resource
7. THE MCP_Server SHALL validate that presented access tokens include the correct audience claim matching the MCP_Server's resource URI
8. THE MCP_Server SHALL NOT hardcode a fixed `client_id` value; it SHALL accept any `client_id` presented by the ChatGPT_App (ChatGPT may use dynamic client registration or a metadata document URL as its client_id)

### Requirement 2: Pairing Code Generation

**User Story:** As a user, I want to initiate pairing from the Desktop_App and receive a short human-readable code, so that I can link my ChatGPT session to my desktop without creating an account.

#### Acceptance Criteria

1. WHEN the user clicks "Connect to ChatGPT" in the Desktop_App, THE Desktop_App SHALL call POST /pairing/start on the MCP_Server over HTTPS
2. WHEN the MCP_Server receives a POST /pairing/start request, THE MCP_Server SHALL generate a Pairing_Code in the format XOXO-XXXX-XXXX where X is an uppercase alphanumeric character excluding visually ambiguous characters (0, O, 1, I, L)
3. THE MCP_Server SHALL create a session placeholder and associate the generated Pairing_Code with it, returning both the code and session ID to the Desktop_App
4. THE MCP_Server SHALL return the Pairing_Code and session ID in the response body to the Desktop_App
5. WHEN the Desktop_App receives the Pairing_Code, THE Desktop_App SHALL display the code prominently to the user
6. THE Pairing_Code SHALL expire 5 minutes after generation
7. IF a Pairing_Code expires without being consumed, THEN THE MCP_Server SHALL remove the code from the pairing store and the Desktop_App SHALL indicate that the code has expired
8. THE MCP_Server SHALL ensure each generated Pairing_Code is unique among all currently active (unexpired) codes
9. THE Desktop_App SHALL establish its WebSocket connection to the MCP_Server independently of the pairing flow, using the session ID returned from /pairing/start to associate itself with the correct session

### Requirement 3: Authorization Endpoint

**User Story:** As a user, I want to enter my pairing code on a web page opened by ChatGPT, so that my ChatGPT session becomes linked to my desktop app session.

#### Acceptance Criteria

1. WHEN the ChatGPT_App navigates to /oauth/authorize with valid OAuth 2.1 parameters (response_type=code, client_id, redirect_uri, state, code_challenge, code_challenge_method), THE MCP_Server SHALL serve an HTML page prompting the user to enter a Pairing_Code
2. THE authorization page SHALL accept a Pairing_Code input in the XOXO-XXXX-XXXX format
3. WHEN the user submits a valid, unexpired Pairing_Code on the authorization page, THE MCP_Server SHALL generate an Authorization_Code, associate it with the Desktop_Session linked to that Pairing_Code, and redirect to the provided redirect_uri with the Authorization_Code and state parameter
4. IF the submitted Pairing_Code is invalid or expired, THEN THE authorization page SHALL display an error message indicating the code is invalid or expired and allow the user to retry
5. THE Authorization_Code SHALL expire 60 seconds after generation
6. THE MCP_Server SHALL consume the Pairing_Code upon successful authorization so that the same code cannot be used again
7. THE authorization page SHALL validate that the required OAuth parameters (response_type, client_id, redirect_uri, code_challenge, code_challenge_method) are present before rendering the pairing code input
8. IF required OAuth parameters are missing or invalid, THEN THE MCP_Server SHALL return an error page describing the missing parameters

### Requirement 4: Token Endpoint

**User Story:** As the ChatGPT_App, I want to exchange an authorization code for an access token, so that I can authenticate subsequent MCP tool calls.

#### Acceptance Criteria

1. WHEN the ChatGPT_App sends a POST request to /oauth/token with grant_type=authorization_code, the Authorization_Code, redirect_uri, client_id, and code_verifier, THE MCP_Server SHALL validate the code_verifier against the stored code_challenge using S256
2. IF the code_verifier does not match the stored code_challenge, THEN THE MCP_Server SHALL return an error response with error code `invalid_grant`
3. IF the Authorization_Code is expired or has already been exchanged, THEN THE MCP_Server SHALL return an error response with error code `invalid_grant`
4. WHEN the Authorization_Code and code_verifier are valid, THE MCP_Server SHALL issue an Access_Token as a JWT signed with the server-side secret
5. THE Access_Token JWT SHALL contain a `sub` claim that identifies the paired Desktop_Session
6. THE Access_Token JWT SHALL contain an `iss` claim set to `https://aix.reflect.systems`
7. THE Access_Token JWT SHALL contain an `exp` claim set to 60 minutes from issuance
8. THE MCP_Server SHALL return the Access_Token in the response body with `token_type: "bearer"` and `expires_in` set to the token lifetime in seconds
9. THE MCP_Server SHALL consume the Authorization_Code upon successful token exchange so that the same code cannot be used again
10. THE token endpoint SHALL be accessible without Bearer token authentication (it is the mechanism for obtaining tokens)
11. THE Access_Token JWT SHALL contain an `aud` claim set to the `resource` parameter value from the token request (the MCP_Server's canonical URI)
12. THE token endpoint SHALL accept and store the `resource` parameter from the token request per RFC 8707

### Requirement 5: Access Token Validation

**User Story:** As a user, I want my MCP tool calls to be authenticated using the access token from pairing, so that only my paired ChatGPT session can access my circuit data.

#### Acceptance Criteria

1. WHEN an MCP tool request includes a Bearer token in the Authorization header, THE MCP_Server SHALL validate the JWT signature using the server-side signing secret
2. IF the Access_Token signature is invalid, THEN THE MCP_Server SHALL return a 401 response with error `malformed`
3. IF the Access_Token has expired, THEN THE MCP_Server SHALL return a 401 response with error `expired`
4. IF the Access_Token `iss` claim does not match `https://aix.reflect.systems`, THEN THE MCP_Server SHALL return a 401 response with error `unrecognized`
5. WHEN the Access_Token is valid, THE MCP_Server SHALL extract the `sub` claim and use it to look up the associated Desktop_Session
6. IF the Desktop_Session referenced by the Access_Token `sub` claim no longer has an active WebSocket connection, THEN THE MCP_Server SHALL return an error indicating the desktop app is not connected
7. THE MCP_Server SHALL replace the current AUTH_DISABLED bypass in the token validation middleware with the self-issued JWT validation logic

### Requirement 6: Desktop Session Linking

**User Story:** As a user, I want my ChatGPT MCP session to be linked to my desktop app's WebSocket session, so that tool calls from ChatGPT can read from and write to my live circuit.

#### Acceptance Criteria

1. WHEN a valid Access_Token is presented with an MCP tool call, THE MCP_Server SHALL resolve the token's `sub` claim to the Desktop_Session that was paired during the authorization flow
2. THE MCP_Server SHALL use the linked Desktop_Session's WebSocket connection to forward write tool requests to the Desktop_App
3. THE MCP_Server SHALL use the linked Desktop_Session's stored state (circuit layout, simulation results, FRD data) to serve read tool responses
4. IF the Desktop_App disconnects its WebSocket after pairing, THEN THE MCP_Server SHALL retain the session data but return an error for write tool calls that require forwarding to the Desktop_App
5. WHEN the Desktop_App reconnects its WebSocket, THE MCP_Server SHALL re-associate the WebSocket connection with the existing session so that subsequent MCP tool calls resume working
6. THE MCP_Server SHALL support multiple concurrent paired sessions (different desktop apps paired with different ChatGPT sessions)

### Requirement 7: Write Tool Desktop Confirmation

**User Story:** As a user, I want write operations from ChatGPT to require my confirmation in the desktop app before executing, so that I maintain control over changes to my circuit.

#### Acceptance Criteria

1. WHEN a Write_Tool is invoked via MCP, THE MCP_Server SHALL forward the request to the Desktop_App and wait for a confirmation response before applying the change
2. THE Desktop_App SHALL present the pending write operation to the user with sufficient context (tool name, description of the change) to make an informed accept/reject decision
3. WHEN the user accepts the write operation in the Desktop_App, THE Desktop_App SHALL apply the change, push to the undo stack, trigger simulation recalculation, and send a success response to the MCP_Server
4. WHEN the user rejects the write operation in the Desktop_App, THE Desktop_App SHALL send a rejection response to the MCP_Server without modifying the circuit
5. IF the user rejects a write operation, THEN THE MCP_Server SHALL return an error to the ChatGPT_App indicating the user declined the change
6. IF the Desktop_App does not respond to a write confirmation request within 30 seconds, THEN THE MCP_Server SHALL return a timeout error to the ChatGPT_App
7. Read_Tool invocations SHALL NOT require desktop confirmation and SHALL return data immediately from the session store

### Requirement 8: Desktop App Pairing UI Flow

**User Story:** As a user, I want a clear flow in the desktop app to initiate and monitor the pairing process, so that I can connect my ChatGPT session with minimal friction.

#### Acceptance Criteria

1. THE Desktop_App SHALL provide a "Connect to ChatGPT" button or menu item that initiates the pairing flow
2. WHEN the user initiates pairing, THE Desktop_App SHALL display the Pairing_Code prominently with instructions to enter it in the ChatGPT authorization page
3. THE Desktop_App SHALL display a countdown or expiration indicator showing the remaining validity time of the Pairing_Code
4. WHEN the pairing is successfully completed (Authorization_Code exchanged for a token), THE MCP_Server SHALL notify the Desktop_App via the WebSocket connection that pairing succeeded
5. WHEN the Desktop_App receives pairing success notification, THE Desktop_App SHALL update its UI to indicate the active ChatGPT connection (e.g., change menu item to "Disconnect ChatGPT")
6. IF the Pairing_Code expires without being used, THEN THE Desktop_App SHALL display a message indicating expiration and offer to generate a new code
7. THE Desktop_App SHALL provide a way to disconnect an active ChatGPT pairing, which invalidates the associated Access_Token on the server

### Requirement 9: Token Signing and Security

**User Story:** As a developer, I want access tokens to be securely signed and validated, so that tokens cannot be forged or tampered with.

#### Acceptance Criteria

1. THE MCP_Server SHALL sign Access_Token JWTs using HMAC-SHA256 (HS256) with a server-side secret key
2. THE server-side signing secret SHALL be configured via an environment variable and SHALL NOT be committed to the repository
3. THE server-side signing secret SHALL be at least 32 bytes (256 bits) in length
4. THE MCP_Server SHALL validate the complete JWT structure (header, payload, signature) before accepting a token
5. THE MCP_Server SHALL reject tokens with algorithms other than HS256 to prevent algorithm confusion attacks
6. THE Pairing_Code character set SHALL exclude visually ambiguous characters (0, O, 1, I, L) to reduce user entry errors
7. THE Authorization_Code SHALL be a cryptographically random string of at least 32 bytes, URL-safe encoded

### Requirement 10: Removal of External OAuth Dependencies

**User Story:** As a developer, I want to remove all Auth0/external OAuth provider dependencies, so that the system is self-contained and does not require third-party authentication services.

#### Acceptance Criteria

1. THE MCP_Server SHALL NOT depend on any external OAuth provider (Auth0, Okta, or similar) for token issuance or validation
2. THE MCP_Server SHALL NOT make outbound network requests to JWKS endpoints for token validation
3. THE server configuration SHALL remove the `jwksUri` and external `issuer` OAuth settings that reference third-party providers, but SHALL retain an `audience` setting set to the MCP_Server's resource URI (`https://aix.reflect.systems/mcp`)
4. THE Desktop_App OAuth configuration SHALL be updated to reference the MCP_Server's own authorization and token endpoints
5. THE WebSocket authentication in the server SHALL validate tokens using the same self-issued JWT validation as the MCP endpoint (HS256 with server secret) instead of RS256 with external JWKS
6. THE `AUTH_DISABLED` environment variable bypass SHALL be removed from the production token validation middleware and replaced with the self-issued token validation logic
